Diagnosis

Three reasons it was slow

3×

Dense solves

Three dense 751×751 factorisations per frequency, for a matrix that is 99.5 % zeros (2,537 non-zeros).

9 GB

Saved for the gradient

The benchmark keeps the forward pass's residuals for the gradient; with plain JAX autodiff that meant every intermediate: ~9 GB. Peak memory ~14 GB.

~50 %

Compilation

XLA compiled all 19 component formulas for every matrix entry, plus their derivatives, in complex arithmetic.

The lesson we kept relearning: profile first. After the solver was fixed, compilation was ~90 % of the score.

Idea 1 of 4

Less linear algebra

  • The noise needs w = A⁻ᴴc and then A⁻¹Qw. Since cᴴA⁻¹ = wᴴ:
    noise ∝ Re(wᴴ Q w)
    so the third solve is redundant.
  • The other two share one sparse LU (SciPy SuperLU) on the fixed 2,597-entry pattern.
  • One step of iterative refinement keeps it accurate on hard setups.

Idea 2 of 4

A hand-written gradient (adjoint method)

For A x = b and the incoming gradient x̄:

λ    = A⁻ᵀ x̄                 ← one extra solve, same LU
b̄    = λ
Ā[k] = −λ[row_k] · x[col_k]  ← non-zeros only

Checked against JAX's own autodiff to 1e-16. The conjugate transpose would be 58 % wrong: JAX uses the plain transpose for holomorphic maps.

Effect

  • We still save residuals for the reverse pass, but only what the gradient needs (inputs, factorisations, solutions): tens of MB instead of ~9 GB
  • No full 751×751 gradient matrix per frequency
  • Memory: the original needs ~14 GB and does not fit in the 7 GB available to WSL2 on our machine; ours runs comfortably
Idea 3 of 4

No physics left for XLA to compile

  • The whole simulation runs as NumPy / SciPy code behind a single jax.custom_vjp.
  • Same physics source: the formulas in components.py are reused unchanged, re-bound to NumPy.
  • Derivatives come from forward-mode dual numbers running that same code.
  • XLA sees only two callbacks.

Startup and compile polish

Setup

  • No tiny XLA compiles while building the setup
  • Plotting and scipy.sparse imports only when needed
  • Build 1.34 s → 0.20 s

XLA options

  • Three compile options set in differometor/__init__.py
  • No number changes (bit-identical outputs)
  • Recorded in the benchmark report; off with DIFFEROMETOR_XLA_OPT0=0

Smaller wins

  • Dual numbers only on the inputs a formula reads
  • Solver ordering reused across frequencies
  • Detector read-outs in NumPy too

What we learned

Four lessons

Profile first

The obvious bottleneck (linear algebra) was half the story; compilation became ~90 %.

Exploit structure

A fixed sparsity pattern means one sparse factorisation, and a gradient on the non-zeros only.

One source of physics

The same component code runs on NumPy and on dual numbers, so there is no second model to keep in sync.

Check every gradient

A strict harness against the original code, covering all outputs, all gradients and many setups, found the bugs the spot check would miss.
